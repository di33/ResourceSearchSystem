# 资源加工服务器设计文档

## 1. 目标

建设独立的资源加工服务器，统一处理来自客户端、3D 模型生成服务、爬虫和已有对象存储资源库的资源入库前加工流程。

资源加工服务器负责：

- 校验对象存储中的原始资源。
- 复用客户端提供的预览，或在缺失时生成预览。
- 复用客户端提供的描述，或在缺失时生成资源描述、标签和分类。
- 将加工结果提交给搜索服务器入库。

搜索服务器负责：

- 保存资源元数据、描述、预览引用和原始资源引用。
- 生成入库向量。
- 写入关键词索引和向量索引。
- 搜索时生成查询向量并执行检索。

## 2. 核心边界

资源加工服务器只消费对象存储引用，不接收原始文件或预览文件的二进制上传。

所有客户端上传的原始资源和预览文件，都必须先进入对象存储。资源加工请求只携带 `bucket + object_key` 以及必要的元数据。

```text
Client / 3D 生成服务 / 爬虫
  -> 上传原始资源到对象存储
  -> 可选：上传预览到对象存储
  -> 提交资源清单给资源加工服务器

资源加工服务器
  -> 读取 source_files
  -> 校验 provided_previews
  -> 有 provided_previews 则复用，否则生成预览
  -> 有 provided_description 则复用，否则生成描述、标签、分类
  -> 上传生成的预览到对象存储
  -> 调用搜索服务器 upsert 接口

搜索服务器
  -> 保存资源记录
  -> 生成 embedding
  -> 写入索引
  -> 提供搜索和详情查询
```

## 3. 组件职责

### 3.1 客户端 / 资源生产方

包括本地客户端、3D 模型生成服务、爬虫和批量导入任务。

职责：

- 将原始资源上传到对象存储。
- 可选地将已有预览上传到对象存储。
- 构造并持久化资源清单，包括对象存储引用、客户端侧资源 ID、可选的客户端自定义元数据和子资源清单。
- 后续从已持久化的资源清单调用资源加工服务器创建加工任务。
- 查询加工状态或接收回调。

客户端提交给资源加工服务器的文件信息必须是对象存储引用。

### 3.2 对象存储

职责：

- 存储原始资源文件。
- 存储客户端提供的预览。
- 存储资源加工服务器生成的预览。
- 存储可下载资源包。

对象存储中的资源通过以下信息稳定定位：

```text
bucket + object_key
```

### 3.3 资源加工服务器

职责：

- 接收资源清单并创建加工任务。
- 校验资源对象是否存在、大小和 checksum 是否匹配。
- 识别资源类型和文件角色。
- 处理多文件资源依赖。
- 处理结构化子资源清单。
- 保存客户端自定义元数据，并在生成描述时作为上下文传给 AI。
- 有客户端预览则校验并复用，否则生成预览。
- 有客户端描述则复用，否则生成描述、标签、分类等语义内容。
- 上传生成的派生产物到对象存储。
- 将最终资源记录提交给搜索服务器。
- 管理任务状态、重试、错误记录和处理日志。

资源加工服务器不生成入库向量。

### 3.4 Processing Worker

资源加工服务器内部可以拆分为多个 Worker。

建议 Worker 类型：

- `metadata-worker`：解包、识别格式、提取基础元数据。
- `preview-worker`：生成图片、视频、3D、Spine 等预览。
- `description-worker`：生成资源描述、标签和分类。
- `dispatch-worker`：提交加工结果到搜索服务器。

Worker 可按能力异构部署，例如 Linux Worker 优先处理 Blender、图片和视频；如 Spine 或特定插件在 Linux 上不可稳定运行，可保留专用 Worker 池。

### 3.5 搜索服务器

职责：

- 接收资源加工服务器提交的最终资源记录。
- 根据描述和结构化字段拼接索引文本。
- 生成入库 embedding。
- 写入数据库、全文索引和向量索引。
- 搜索时使用同一套 embedding 接口生成查询向量。
- 提供搜索、过滤、排序和资源详情查询。

embedding 能力放在搜索服务器侧，以保证入库向量和查询向量使用同一模型、同一配置和同一版本策略。

### 3.6 代码目录与部署边界

资源加工服务器和搜索服务器是两个可独立部署的服务，不应把资源加工能力放入搜索服务器目录内。

建议代码目录：

```text
ResourceUpload/
  client/
  SearchServer/                  # 搜索服务器
  resource_processing_server/    # 新增资源加工服务器
  Design/
  specs/
```

搜索服务器目录命名为 `SearchServer`，只承载资源 upsert、embedding、索引和搜索能力。

部署关系：

- `resource_processing_server` 独立部署，负责创建加工任务、调度 Worker、生成预览和描述。
- `SearchServer` 独立部署，负责资源 upsert、embedding、索引和搜索。
- 两个服务通过 HTTP 或内部 RPC 调用，不通过本地 import 耦合。
- 搜索服务器拥有索引数据库和向量索引的写入逻辑。
- 资源加工服务器不直接写搜索服务器数据库，只调用搜索服务器的 upsert 接口。
- 两个服务可以分别扩容，资源加工 Worker 可按 CPU/GPU/插件能力单独扩容。

## 4. 对象引用模型

所有文件引用统一使用对象存储引用。

```json
{
  "bucket": "asset-bucket",
  "object_key": "raw/models/chair/chair.glb",
  "version_id": "",
  "etag": "",
  "checksum": "md5-or-sha256",
  "size": 123456,
  "content_type": "model/gltf-binary"
}
```

字段说明：

- `bucket`：对象存储桶名。
- `object_key`：对象在桶内的唯一 key。
- `version_id`：对象版本，可选。
- `etag`：对象存储返回的 ETag，可选。
- `checksum`：客户端计算的内容校验值，建议提供。
- `size`：文件大小，建议提供。
- `content_type`：文件 MIME 类型，建议提供。

## 5. 资源清单

创建加工任务时，客户端提交资源清单。

资源清单由少量服务端协议字段和一个客户端自定义 JSON 字段组成。服务端只理解协议字段；客户端自定义字段只作为描述生成上下文和原始信息保存。

```json
{
  "request_id": "client-generated-id",
  "client_resource_id": "external-resource-id",
  "resource_type": "model_3d",
  "source_files": [
    {
      "role": "main",
      "bucket": "asset-bucket",
      "object_key": "model-generator-client/files/external-resource-id/chair.glb",
      "file_name": "chair.glb",
      "file_format": "glb",
      "content_type": "model/gltf-binary",
      "size": 123456,
      "checksum": "..."
    }
  ],
  "provided_previews": [
    {
      "role": "primary",
      "bucket": "asset-bucket",
      "object_key": "previews/models/chair/primary.webp",
      "content_type": "image/webp",
      "width": 1024,
      "height": 1024,
      "size": 45678,
      "checksum": "..."
    }
  ],
  "provided_description": {
    "main_content": "客户端已有主描述",
    "detail_content": "客户端已有详细描述",
    "prompt_version": "client-provided-v1",
    "source": "client"
  },
  "client_metadata": {
    "title": "Modern Chair",
    "category": "Furniture/Chair",
    "tags": ["chair", "wood", "modern"],
    "source_description": "Original description from source site.",
    "generation_prompt": "a modern wooden chair with fabric cushion",
    "generation_parameters": {
      "seed": 12345
    }
  },
  "child_resources": [
    {
      "client_resource_id": "external-child-id-1",
      "resource_type": "texture",
      "relationship": "contains",
      "source_files": [
        {
          "role": "main",
          "bucket": "asset-bucket",
          "object_key": "raw/models/chair/textures/diffuse.png",
          "file_name": "diffuse.png",
          "file_format": "png",
          "content_type": "image/png",
          "size": 12345,
          "checksum": "..."
        }
      ],
      "client_metadata": null
    }
  ],
  "callback_url": ""
}
```

`client_resource_id` 是客户端侧资源 ID，只要求在当前客户端内唯一。资源加工服务器必须结合认证得到的 `client_id` 形成全局唯一身份：

```text
global_source_key = client_id + client_resource_id
```

客户端不需要保证自己的资源 ID 和其他客户端不冲突，服务端也不能只用 `client_resource_id` 做全局唯一键。

### 5.1 source_files

`source_files` 不能为空。

多文件资源必须把相关文件全部列出，例如：

- `glb`：通常单文件。
- `gltf`：`gltf + bin + textures`。
- `obj`：`obj + mtl + textures`。
- `spine`：`json/skel + atlas + png`。
- `fbx`：`fbx + external textures`。
- `pack`：资源包及其子资源清单。

常用 `role`：

- `main`
- `material`
- `texture`
- `skeleton`
- `atlas`
- `animation`
- `download_package`
- `metadata`

### 5.2 provided_previews

`provided_previews` 可为空。

客户端提供预览时，预览文件也必须已经在对象存储中，并通过 `bucket + object_key` 引用。

常用 `role`：

- `primary`
- `gallery`
- `thumbnail`
- `detail`
- `animation`

### 5.3 client_metadata

### 5.3 provided_description

`provided_description` 可为空或省略。

客户端提供描述时，服务端固定复用该描述并跳过描述生成；客户端不传描述时，服务端生成描述。客户端不传入 `description_policy`，也不决定服务端策略。

描述字段建议包括：

- `main_content`：主描述。
- `detail_content`：详细描述。
- `prompt_version`：客户端描述来源或生成版本。
- `usage_*`：可选用途分类字段。

### 5.4 client_metadata

`client_metadata` 是客户端自定义 JSON，可为对象、数组、字符串、数字、布尔值或 `null`。

资源加工服务器不理解其中字段含义，不基于其中字段做协议级判断。它的用途是：

- 作为生成描述时的上下文输入。
- 作为来源原始信息原样保存。
- 提交给搜索服务器保存，便于后续溯源、纠错和重跑。

典型内容包括：

- 爬虫得到的名称、分类、标签、原描述、作者、来源页面、授权信息。
- 3D 模型生成服务的提示词、负向提示词、生成模型、生成参数。
- 客户端已有的业务字段。

如果客户端没有可提供的信息，应传 `null` 或省略该字段。

### 5.5 child_resources

`child_resources` 是服务端需要理解的结构化字段，用于描述包资源、父子资源、资源拆分和派生资源。

子资源中的 `client_resource_id` 仍然是客户端侧 ID，只在同一个 `client_id` 命名空间内唯一。资源加工服务器需要为每个子资源生成自己的全局资源 ID，并维护父子关系。

子资源清单可以包含：

- `client_resource_id`：客户端侧子资源 ID。
- `resource_type`：子资源类型。
- `relationship`：关系类型，例如 `contains`、`derived_from`、`variant_of`。
- `source_files`：子资源文件引用。
- `provided_previews`：子资源预览引用，可选。
- `provided_description`：子资源描述，可选。
- `client_metadata`：子资源的客户端自定义 JSON，可为 `null`。

父子关系入库时应保存：

```text
parent_resource_id      服务端全局资源 ID
child_resource_id       服务端全局资源 ID
parent_client_id        来源客户端 ID
parent_client_resource_id
child_client_id         来源客户端 ID
child_client_resource_id
relationship
```

## 6. 预览处理

资源加工服务器必须校验客户端提供的预览：

- 对象存在。
- bucket 和 prefix 在白名单内。
- content type 合法。
- 文件大小在限制范围内。
- 图片可解码。
- 宽高符合要求。
- checksum 或 etag 匹配。

服务端固定按以下规则处理：

- 有 `provided_previews`：校验并复用；校验失败则任务失败。
- 没有 `provided_previews`：生成预览。

客户端不传入 `preview_policy`，也不决定服务端策略。

预览记录需要保存来源：

```text
origin = provided | generated | reused | placeholder
renderer = client | blender | spine | ffmpeg | image
renderer_version = ...
```

## 7. 描述生成

服务端固定按以下规则处理：

- 有 `provided_description`：复用客户端描述，跳过描述生成。
- 没有 `provided_description`：进入描述生成队列。

资源加工服务器基于以下输入生成描述：

- 原始资源文件名和路径。
- 资源类型。
- 客户端提交的 `client_metadata` 原始 JSON。
- 提取出的结构化元数据。
- 有效预览图。
- 多文件资源的依赖结构。

输出建议包括：

```json
{
  "title": "现代木质餐椅模型",
  "summary": "一款带软垫座面的现代风格木质餐椅，适合室内、餐厅和家具可视化场景。",
  "detail": "模型包含主体结构、座面和靠背，材质表现为木材与布料组合。",
  "category": "家具/椅子",
  "tags": ["餐椅", "木质", "软垫", "现代", "室内"],
  "style": ["现代", "简约"],
  "materials": ["木材", "布料"],
  "use_cases": ["室内设计", "建筑可视化", "游戏场景"],
  "quality_notes": ["包含贴图", "适合实时渲染"],
  "confidence": 0.86
}
```

描述结果需要记录：

- 生成模型。
- prompt 版本。
- 生成时间。
- 输入预览版本。
- 置信度。
- 校验结果。

描述生成支持按数量和等待时间聚合为批处理任务。建议触发条件：

- 待生成描述数量达到 `BATCH_MIN_SIZE`。
- 或最早待处理描述等待超过 `BATCH_MAX_WAIT_SECONDS`。
- 或累计请求大小接近 provider 限制。

如果 provider 支持文件式 Batch API，可由 `description-worker` 将待生成描述任务转换为 JSONL，并用 `job_id` 或 `client_id:client_resource_id` 作为 `custom_id` 回填结果。若 provider 不支持 Batch API，则退化为并发单请求。

资源加工服务器对外提供两个提交接口：

```text
POST /processing-jobs
POST /processing-jobs/batch
```

批量接口只负责批量创建任务；内部仍保持一个资源一个 job，以便单资源失败、重试、取消和状态查询。

## 8. 提交给搜索服务器

资源加工服务器在调用搜索服务器前，需要保存最近一次成功加工快照。快照用于 SearchServer upsert 失败、清库或重新部署后的恢复回放，不用于搜索。

快照只保存：

- 原始资源对象引用。
- 选中的预览对象引用。
- 选中的描述和分类结果。
- 客户端自定义元数据。
- 父子关系。
- processing 元数据和 SearchServer upsert 状态。

快照不保存：

- 原始资源二进制。
- 预览二进制。
- embedding。
- 全文索引或向量索引。

同一个 `client_id + client_resource_id` 只保留最新一次成功加工快照。

加工完成后，资源加工服务器调用搜索服务器 upsert 接口。

```text
POST /resources/upsert
```

## 9. 资源加工 API

### 9.1 创建任务

```text
POST /processing-jobs
```

返回：

```json
{
  "job_id": "job_123",
  "state": "queued",
  "resource_fingerprint": "..."
}
```

### 9.2 批量创建任务

```text
POST /processing-jobs/batch
```

请求体：

```json
{
  "request_id": "client-batch-id",
  "manifests": []
}
```

返回：

```json
{
  "batch_id": "batch_123",
  "jobs": [
    {
      "job_id": "job_123",
      "client_resource_id": "external-resource-id",
      "state": "queued",
      "resource_fingerprint": "..."
    }
  ]
}
```

### 9.3 查询任务

```text
GET /processing-jobs/{job_id}
```

返回：

```json
{
  "job_id": "job_123",
  "state": "completed",
  "client_resource_id": "external-resource-id",
  "search_resource_id": "res_xxx",
  "steps": [
    {
      "name": "validate_objects",
      "state": "completed",
      "duration_ms": 120

    {
      "name": "preview",

      "duration_ms": 3500

    {
      "name": "search_upsert",
```


```text
POST /processing-jobs/{job_id}/cancel
```

### 9.6 回放加工快照

```text
POST /processed-resource-snapshots/{client_resource_id}/replay
POST /processed-resource-snapshots/replay
```

用于 SearchServer upsert 失败、清库或重新部署后，把资源加工服务器保存的最新加工快照重新提交给 SearchServer。

## 10. 状态机

任务状态：

```text
queued
  -> validating
  -> validated
  -> previewing
  -> describing
  -> submitting
  -> completed
```

失败状态：

```text
failed
cancelled
```

可重试步骤：

- 对象读取失败。
- 预览生成失败。
- 描述生成失败。
- 上传生成预览失败。
- 提交搜索服务器失败。

不可自动重试错误：

- bucket 不在白名单。
- object_key 不在允许 prefix。
- 对象不存在。
- checksum 不匹配。
- 文件格式不支持。
- manifest 缺少必要文件。

## 11. 安全规则

资源加工服务器读取对象时必须执行安全校验：

- 只允许白名单 bucket。
- 只允许白名单 object key prefix。
- 不接受任意 HTTP URL 作为正式输入。
- 限制单文件大小和总资源大小。
- 限制支持的扩展名和 content type。
- 校验 checksum、etag 或对象版本。
- 下载到隔离工作目录。
- 解包时防止路径穿越。
- 每个任务设置超时和磁盘配额。
- Worker 进程隔离执行高风险解析和渲染逻辑。

## 12. 幂等与去重

客户端必须提供 `request_id` 或稳定的 `client_resource_id`。

`client_id` 由认证信息、调用凭证或服务端分配的接入方身份确定，不应完全信任请求体中的同名字段。

客户端侧资源 ID 的唯一约束是：

```text
unique(client_id, client_resource_id)
```

资源加工服务器生成资源指纹：

```text
fingerprint = hash(source_files.bucket + source_files.object_key + checksum/version)
```

幂等规则：

- 相同 `client_id + request_id` 重复提交，返回同一任务或同一结果。
- 相同 `client_id + client_resource_id` 可覆盖更新同一个来源资源。
- 相同资源指纹可跳过重复加工。
- 子资源关系必须使用 `client_id + client_resource_id` 解析到服务端全局资源 ID。
- 预览和描述需要记录生成版本，支持后续按版本重跑。

## 13. 存储路径建议

原始资源由客户端决定存储位置。推荐对象 key 结构：

- 原文件：`{client_id}/files/{client_resource_id}/{relative_path}`
- 预览：`{client_id}/previews/{client_resource_id}/{preview_name}`
- 多预览命名：`primary.{ext}`、`gallery-001.{ext}`、`gallery-002.{ext}`
- `pack` 资源上传为 `{client_id}/files/{client_resource_id}/pack.zip`，zip 内保留成员文件相对路径。

资源加工服务器生成的预览也写入同一套 `previews` 结构，来源由 manifest/DB 中的 `origin=generated` 区分。若同一 bucket 需要环境隔离，可在最前面增加可选根前缀。

```text
{client_id}/files/{client_resource_id}/chair.glb
{client_id}/files/{client_resource_id}/pack.zip
{client_id}/previews/{client_resource_id}/primary.webp
{client_id}/previews/{client_resource_id}/gallery-001.webp
processed/work/{job_id}/...
```

加工完成后，临时工作区可清理；对象存储中的生成预览长期保留。

## 14. Linux 部署验证

预览能力需要按资源类型做 Linux 服务端验证。

验证项：

- 是否有 Linux 可执行版本。
- 是否支持命令行或 headless 模式。
- 是否必须依赖 GUI。
- 如依赖 GUI，是否可通过 Xvfb 稳定运行。
- 授权是否允许服务器自动化运行。
- license 激活是否支持容器或服务器环境。
- 批量任务是否会弹窗或阻塞。
- 异常输入是否能稳定超时退出。
- 并发多个进程是否安全。
- 输出格式是否可控。

部署原则：

- API 服务优先部署在 Linux。
- Worker 按能力分池。
- Blender、图片、视频优先 Linux Worker。
- 特定插件如无法稳定运行在 Linux，可部署专用 Worker，并通过同一任务协议接入。

## 15. 最终原则

- 原始资源和客户端预览都必须先进入对象存储。
- 资源加工服务器只接收 `bucket + object_key` 资源清单。
- 客户端自定义信息统一放入 `client_metadata`，允许为 `null`，服务端不解释字段含义。
- 子资源清单是服务端理解的结构化字段，资源 ID 必须按 `client_id + client_resource_id` 命名空间处理。
- 资源加工服务器负责预览、描述、标签和分类。
- 搜索服务器负责 embedding、索引和搜索。
- 资源加工服务器和搜索服务器是平级服务，代码目录和部署单元独立。
- 资源加工服务器通过搜索服务器 API 入库，不直接写搜索服务器数据库。
- 客户端提供的预览可以复用，但必须校验。
- 客户端提供的描述可以复用；服务端根据是否存在 `provided_description` 决定是否生成描述。
- 客户端不传入预览或描述生成策略。
- 多文件资源必须以完整清单提交。
- 所有生成结果必须记录来源、版本和可重跑信息。
